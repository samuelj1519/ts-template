## 2. 已核实的现状与责任边界

仓库通过 `scaffold/common/`、`scaffold/presets/<preset>/`、`scaffold/presets.json`、`scaffold/locks/<preset>.json` 组装到 `templates/<preset>`，根目录镜像 vanilla。`tools/template-tests/src/assembly.ts` 目前只验证 npm v3 锁；`locks.ts` 只调用真实 npm 生成三个权威锁，全部生成并验证后才写入。`registry.ts` 严格限制三个预设，不能直接增加九个预设 ID 来代替选项建模。

`tools/template-tests/tests/generation.test.ts` 目前会调用安装、完整里程碑及负例。它的 `npm run check` 不是廉价的只读入口，本阶段没有运行。后续必须拆开静态契约、安装验收和里程碑调度，不能只在 CI 名称上改成 pairwise，而内部仍对每个变体运行里程碑。

当前 `licenses.ts` 扫描实际 `node_modules` 中的生产依赖，允许 `MIT;ISC;BSD-2-Clause;BSD-3-Clause;Apache-2.0`，并检查每个直接生产依赖都有报告。当前门槛为覆盖率 100%、模型变异分 100%、指定源码重复率为零。本文不建议降低任何门槛。

后续职责保持集中：registry 定义有限组合，composer 纯粹组装文件，包管理器适配器负责命令和锁格式，检查器解析外部文件后接收明确数据。应用纯模型不接触包管理器、文件系统或 UI。清单、锁、生成物和共享契约分别指定唯一写入者，不并发改同一对象。

## 3. 包管理器选项

### 3.1 变体的具体差异

| 位置或行为       | npm 默认                                                                    | Bun 变体                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `packageManager` | `npm@12.2.2`                                                                | `bun@1.3.11`                                                                                                                   |
| 唯一锁文件       | `package-lock.json`                                                         | 文本 `bun.lock`                                                                                                                |
| `engines`        | 保留 `node: >=26.13.1 <27`、`npm: >=12.2.2 <13`                             | 保留相同 Node 范围；删除 npm 项，增加 `bun: >=1.3.11 <1.4`；CI 和检查器另核对精确版本 1.3.11                                   |
| 安装             | `npm ci`                                                                    | `bun install --frozen-lockfile`；不得在 frozen 失败后退回普通 install                                                          |
| 脚本调度         | `npm run <script>`                                                          | `bun run <script>`；保留显式 `run`，避免与 `bun test` 等内建命令冲突                                                           |
| 嵌套脚本         | `build`、`test:e2e`、`test:mutation`、三个 check 入口内的 `npm run`         | 生成时按受控脚本键替换成 `bun run`，不用全文字符串替换                                                                         |
| 工具宿主         | `node tools/checks/*.ts`、Node test runner                                  | 保持 Node；不改成 Bun runtime，不使用 `--bun`，保留 `process.execPath` 启动子进程的约定                                        |
| 工具测试         | `node --test tools/checks/*.test.ts`                                        | 同一命令；应用测试仍为 Vitest，不能换成 Bun 内建 test                                                                          |
| hooks、指南      | `.githooks/pre-commit` 和 README 中 npm 命令                                | 生成 Bun 对应版本，hook 调 `bun run check`；所有独立项目命令须与所选管理器一致                                                 |
| Playwright       | 安装依赖后执行 `node node_modules/@playwright/test/cli.js install chromium` | 使用同一路径和 Node；Linux CI 加 `--with-deps`，macOS、Windows 用 `install chromium`；不使用可能下载另一版本的 `bunx` 或 `npx` |
| 安全扫描         | `npm audit --audit-level=low`                                               | `bun audit --audit-level=low`，覆盖开发与生产依赖；不得只加 `--prod` 缩小范围                                                  |
| 许可证           | 现有生产依赖检查                                                            | 先验证原检查器在 Bun 的实际安装树上完整，再原样使用；不凭 Bun 兼容 npm 就推断兼容                                              |

`bun run` 默认尊重 CLI 的 Node shebang，见 [Bun 脚本执行](https://bun.sh/docs/runtime#run-a-packagejson-script)。这是保留 Node 宿主的依据；当前官网包含晚于 1.3.11 的能力，固定版本仍须真实验收。Bun `engines` 的强制执行不能依赖安装器，项目检查器须直接读取运行版本。`.npmrc` 的 `engine-strict=true` 不足以约束 Bun。维护工具宿主 `tools/template-tests` 继续 npm、TS 7，不要求同时维护两个版本的维护器。

模板代码不得引入 `Bun.*`、`bun:*`、`bun` 的 runtime import、`@types/bun` 或 Bun 专用全局类型。应用沿用 Web API，工具沿用 Node API。快检加入 AST/import 检查，覆盖别名和计算属性等可绕过写法的样例；不能只搜索 `Bun.` 就宣称完整。依赖自身使用的实现细节不算模板源码违规，仍须通过目标 Node 宿主验收。

### 3.2 锁文件和安装边界

每个独立项目根必须恰好存在一个允许的锁。双锁、无锁、错误管理器字段、锁内根依赖或版本与 manifest 不符均失败，同时拒绝旧 `bun.lockb` 和其它管理器锁。规则逐项目执行，不把维护仓库中 12 个项目各自的锁误认为双锁。

快检不联网、不生成锁、不自动删文件。失败须指出路径、所选管理器、发现的锁和修复命令，例如「Bun 变体同时包含 package-lock.json 和 bun.lock；保留已审核的 bun.lock，按任务流程核对并移除误入的 npm 锁，再运行 bun run check」。删除仍遵守授权。

Bun 锁生成拟用 `bun install --lockfile-only --ignore-scripts`，仅在获准的维护 staging 中执行。官方说明即使 lockfile-only 仍可能填充缓存，因此本阶段禁止执行。不能把 npm 锁改名为 `bun.lock`，也不能将迁移成功当作图等价证据。[Bun 锁文件说明](https://bun.sh/docs/pm/lockfile)

Bun 默认的依赖生命周期脚本信任行为与 npm 不同，需逐项确认 SWC、构建器及原生二进制是否已可用。优先不新增 `trustedDependencies`；如确实需要，列明精确包、脚本、副作用和理由，由 Nika 单独批准，不设置全局信任、不把忽略脚本造成的缺件当作应用错误。[Bun 生命周期脚本](https://bun.sh/docs/pm/lifecycle)

### 3.3 Bun 安全和许可证检查的交回条件

Bun 有原生 audit。固定 1.3.11 源码存在 `--audit-level`、`--json` 和生产依赖过滤，读取锁后查询 advisory。当前官网与旧版的 JSON 退出码说明不完全一致，旧源码注释与实现也不完全一致。因此阻断门使用普通文本命令的真实退出码，同时检查 stderr 中的 skipped、请求失败和无法解析结果；JSON 只用于独立留证，不能覆盖门的结果。[1.3.11 audit 实现](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.11/src/cli/audit_command.zig)、[当前 audit 文档](https://bun.sh/docs/pm/cli/audit)

批准后用独立虚构依赖项目分别验证干净图退出 0、已知漏洞图退出非零、网络失败退出非零、被跳过的 registry 包不能绿灯。漏洞样例只审计锁，禁止执行依赖源码。审计数据有日期，不能长期复用旧通过结果。若 1.3.11 无法达到同等阻断，暂停交付 Bun 变体；另提覆盖实际 Bun 锁依赖图的替代审计适配器审批，不能运行 npm install 生成另一张图来冒充 Bun 审计，也不能关闭安全门。

许可证检查先对 vanilla 空生产图、React 和 Vue 非空图运行现有 `node tools/checks/licenses.ts`。独立核对实际生产传递闭包内每个 name/version 的许可证和报告覆盖，不只核对三个直接包。注入禁止许可证、缺 LICENSE、遗漏一个传递依赖的报告，必须非零退出。若原工具因 Bun 布局漏报，先修扫描适配，沿用现有允许清单；不能扩大允许清单来通过。Bun 工具自身及其静态链接库的许可证单独列在第 8 节，不算浏览器生产依赖。

## 4. TypeScript 选项及 Vue 决策

### 4.1 一份配置支持两个版本

「一份」指一套权威 `scaffold/common/tsconfig.base.json` 加现有各预设的轻量 `tsconfig.json`，同一预设在 npm、Bun、TS 6、TS 7 下字节相同，不建 `tsconfig.ts6.json`、`tsconfig.ts7.json`。React 保留 `jsx: react-jsx` 的预设差异，不算版本分叉。维护器自己的 tsconfig 不属于成品的版本选项。

保留当前 `target: ES2023`、`module: ESNext`、`moduleResolution: bundler`、显式 `types`、严格检查及以 `./src/*` 为值的 paths。建议显式统一 `noUncheckedSideEffectImports: true`、`libReplacement: false`、`rootDir: .`，并在过渡期间设 `stableTypeOrdering: true`。这些是拟议配置，须先在 6.0.3 与 7.0.2 上验证。不得用 `ignoreDeprecations` 压掉不兼容。

任务单举例中的 `stableTypeOrdering` 需要纠正：TS 6.0 已引入这个选项，官方将它用于与 TS 7 的类型排序对齐。TS 6 默认不启用，TS 7 固定启用。它不是「TS 6 不认识的新选项」；设置为 true 的本地运行结果本阶段未验证。配置补齐默认值的依据见 [TS 7 发布说明](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)，排序及潜在性能代价见 [TS 6 发布说明](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/#the-stabletypeordering-flag)。

快检采用 JSONC 配置解析和固定版本的选项交集策略：遍历入口、全部 extends 和 references，报告原文件及选项位置；遇到未解析路径、循环、未知选项或不在共享策略内的选项就失败，不悄悄跳过。继承链覆盖 npm 包配置时也必须解析实际文件，不能只读项目根。预设允许集合取两个版本都支持且本项目允许的交集，新增选项需补双版本证据后才纳入。内置 TypeScript 7 不再提供旧 compiler API，不能在工具中假定 `typescript.parseJsonConfigFileContent` 可用；拟新增 `jsonc-parser@3.3.1` 解析 JSONC 和 Bun 文本锁，必须检查解析错误和重复键，再由项目 schema 验证结构，不自行写删注释正则。它是待批开发依赖，详见第 8 节；不调用未公开的 TypeScript API。[jsonc-parser 3.3.1](https://github.com/microsoft/node-jsonc-parser/tree/v3.3.1)

### 4.2 Vue 两条路径

| 选择                                            | 收益                                                              | 代价与阻断项                                                                                           |
| ----------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 保留纯 `.ts`，默认 TS 7，另提供 TS 6 变体，推荐 | 完整保留现有模型、组件、架构和覆盖口径；三默认组合都能 npm + TS 7 | 与常见 SFC 开发体验不同；README 必须明确不支持 `.vue`，继续验证拒绝行为                                |
| Vue 改成 SFC + TS 6                             | 贴近 Vue 常用组件写法，`vue-tsc` 检查脚本与模板                   | 增加 plugin、解析器、模板类型检查及 SFC 架构/覆盖采集适配；无法同时声称 Vue 默认 TS 7、12 个组合均可用 |

官方推荐 SFC 配合 `vue-tsc`，但 `vue-tsc@3.3.14` 的宽 peer `typescript >=5.0.0` 不能证明支持 TS 7。其固定版本入口仍加载旧 tsc 并使用 `ts.sys` 等接口。因此在本方案中 SFC 必须约束为 TS 6，直至真实验证新的接口适配。[Vue TypeScript 指南](https://vuejs.org/guide/typescript/overview.html)、[vue-tsc 3.3.14 入口](https://raw.githubusercontent.com/vuejs/language-tools/v3.3.14/packages/tsc/index.ts)

若 Nika 选择 SFC，需先批准两项规格变化：Vue 的默认组合由 npm + TS 7 改成 npm + TS 6；纯笛卡尔积从 12 个有效组合减为 10 个，Vue 的两个 TS 7 输入明确拒绝，静态注册表仍检查这两个禁配。另一种保持 12 个目录的办法是 TS 7 Vue 继续 render、TS 6 Vue 改 SFC，但这会把编译器选择和源码形式绑在一起，增加两套验收，不推荐。未经批准，执行本方案的 12 组合、纯 `.ts` Vue 路径。

SFC 若立项，除第 8 节条件依赖，还须在 Node 中解析 `.vue`，将 `<script setup>` 和模板依赖纳入架构，覆盖 script 与 template 的类型错误、别名、纯模型边界、真实非空依赖图、Knip、重复检查、覆盖与变异范围。不能用 `declare module '*.vue'` 返回宽类型掩盖错误，也不能直接把 `.vue` 从统计排除。原 `verifyUnsupportedSfc` 的迁移须由指定测试负责人另单处理并获批准，保留等价负例和新 SFC 正例。

### 4.3 TS 6 的机器复查和退出

TS 6 是补坑兼容，首次复查日期建议为 `2026-12-16T00:00:00Z`，之后最多每 30 天复查一次，由 Nika 确认。拟在维护权威输入和 TS 6 成品中记录结构化的 `reviewBy`、负责人、临时原因、退出条件和证据位置，检查器验证日期合法，禁止把无日期当作无限期支持。

到期策略：成品 `check` 输出明确警告及复查链接，不因用户多年后打开项目就自动禁止开发；维护仓库的定期检查 job 读取同一日期，到期返回非零并阻断下一次模板交付。每天定时和手动触发，UTC 比较 `now >= reviewBy` 即过期，检查不联网也能判断。测试覆盖临界点前、等于、之后及缺失日期，使用注入时钟，不能改系统时间。到期不能自动顺延；延期须附生态核对结果与 Nika 批准。

退出必须同时具备：TS 7.1 或之后正式稳定版公开所需新编程接口；vue-tsc、Svelte/Astro 工具、typescript-eslint、Stryker 官方已适配且固定版本实测通过；两次连续完整复查都满足当前类型、lint、构建、浏览器及变异要求；Nika 明确批准。7.1 beta、宽 peer 或单次通过均不足。Svelte/Astro 本项目没有预设，复查它们的官方支持声明并安排独立最小样例，不为复查把它们加进模板。[TS 7 后续 API 说明](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)

批准退出后删除 TS 6 变体、分拆 lint 适配和专用过渡配置，更新组合表与用户迁移说明。永久保留锁唯一、有效 tsconfig、类型感知规则保护和真实验收；`stableTypeOrdering: true` 的显式过渡设置可随 TS 6 退出一起评估删除，不能连带取消类型检查。

## 5. 创建机制比较及推荐结构

| 维度           | A：12 个已提交成品                                                                          | B：复制后切换并在线解析                                                           |
| -------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 供应链可审核性 | 每个 manifest、解析结果、integrity、许可证与 advisory 可在交付前审查；frozen 安装重现选定图 | 复制时只有起点锁可审；切换时的传递版本依赖当时 registry，不能把模板审查扩张到新图 |
| 仓库与维护成本 | 成品文件与锁重复；生成器和矩阵维护成本较高                                                  | 目录少，但要增加用户侧切换、错误处理、联网、重新审核和恢复说明                    |
| 同步漂移       | 若手改成品容易漂移；靠单一权威、12 组字节比对和受控生成拦截                                 | manifest、脚本、工具版本和 CI 可能切一半，锁未知结果更难恢复                      |
| 离线           | 本地已提交源和已准备的 giget 可离线复制成品；安装仍需匹配缓存，audit 仍需网络               | 切换通常需要在线解析；不能承诺离线切换成功                                        |
| giget 入口     | 直接选择有限目录，无创建后动作                                                              | 先选预设再执行切换，路径不能表达最终可审核成品                                    |
| 现有机制改动   | 扩展 registry/composer/lock adapter/契约矩阵；复用当前保护和三份锁机制                      | 保留三个起点目录但新增出厂后修改程序；锁验证和契约仍须支持所有结果，并非免维护    |

推荐 A，采用「生成器批量生成，锁逐个审查」的实现办法，不把锁更新留给最终用户。组合 ID 用三元组 `(preset, packageManager, typescriptMajor)`，不引入插件式任意 overlay。root 固定 vanilla/npm/TS 7，维护器固定 npm/TS 7。

每个预设的四个成品命名为：`templates/<preset>` 对应 npm/TS 7，`templates/<preset>-npm-ts6`、`templates/<preset>-bun-ts7`、`templates/<preset>-bun-ts6`。三个现有路径保持可用，总数恰好 12，不额外生成默认别名目录。Bun + TS 6 的本地创建示例为：

```sh
npm exec --yes --package=giget@3.3.1 -- giget 'git:/absolute/path/to/ts-template#main:templates/vanilla-bun-ts6' my-app
```

创建器本身用 npm 不改变成品所选管理器；复制后只运行 `bun install --frozen-lockfile`、`bun run dev`。示例仅供未来使用，本阶段没有执行。对外发布后再给出带准确已发布 revision 的 `gh:samuelj1519/ts-template/templates/vanilla-bun-ts6#<revision>` 配方并真实验证，不能用当前已配置 origin 推断远程已含这些目录。[giget 源与子目录格式](https://github.com/unjs/giget)

拟采用 `scaffold/locks/<preset>/<manager>-ts<major>.<json|lock>` 保存 12 份权威锁，对成品分别输出唯一规定名称。`scaffold/presets/` 仍只有三个框架源，公共源只保留一套，管理器和版本差异由有限、可审的字段变换产生。composer 不调用安装器；`templates:sync` 只消费已审核锁；`templates:check` 纯离线比较路径、字节、权限和根镜像。

锁更新阶段先在各自独立 staging 生成全部 manifest，再使用对应精确管理器解析，逐份检查根字段、peer、传递版本、integrity、生产许可证及安全报告。npm 与 Bun 的解析图不要求字节或传递版本完全相同，但每份都须审核。只有整批都通过后才替换权威锁；安装或审计结果未知时查询原进程和日志，禁止直接再生成一遍。不要自行承诺跨 12 文件的断电原子性，交付前的完整校验必须发现半批更新并拒绝发布。

当前测得三个权威 npm 锁合计 1,072,268 字节，三个成品约 1.7 MiB，后者为 `du -sk templates` 的分配空间换算。按成品数量四倍粗估约 6.8 MiB，只是同量级预算；Bun 格式、ESLint 传递图和 Git 压缩会改变结果，不能当作精确增量或性能结论。

### 6.2 六组 pairwise 及覆盖证明

真实安装后执行所选管理器的 `run check:full`，选择全量层，不只跑 `check`。因此每组包含单元覆盖、policy、实际构建与浏览器、安全、许可证、未使用项。运行前安装对应已审核锁，使用现有精确 Playwright 的 Chromium。

| 编号        | 预设    | 管理器 | TS  | 原因                                       |
| ----------- | ------- | ------ | --- | ------------------------------------------ |
| A           | vanilla | npm    | 7   | 默认基准                                   |
| B           | vanilla | Bun    | 6   | Node 工具运行于 Bun 安装树，TS 6 分拆 lint |
| C           | react   | npm    | 6   | React 类型、Hooks 及 TS 6 lint             |
| D           | react   | Bun    | 7   | Bun 安装原生工具、TS 7 类型感知            |
| E           | vue     | npm    | 6   | 已知风险，Vue 类型推导和 TS 6              |
| F           | vue     | Bun    | 7   | Vue 依赖图与 Bun                           |
| G，额外必跑 | vue     | Bun    | 6   | 三维交互风险，不能由两两覆盖推断           |

覆盖证明：预设 × 管理器的六对分别由 A、B、C、D、E、F 覆盖；预设 × TS 的六对同样全部由 A–F 覆盖。管理器 × TS 的四对为 npm/7=A、npm/6=C 或 E、Bun/7=D 或 F、Bun/6=B。总计 6+6+4=16 个取值对全部覆盖，G 是风险追加而非 pairwise 缺口。实现时由静态断言从矩阵枚举这 16 对，删去任一必要行必须报出缺失对。

独立风险清单包括 E 的 Vue + TS 6、G 的 Vue + Bun + TS 6、C 的 React + TS 6、D 的 React + Bun + TS 7、B 的无框架 Bun + TS 6。E、G 必须按 ID 固定要求存在，不能在后续重排 pairwise 时丢失；C、D、B 的原因也进入风险登记。如果选择 SFC，E/G 还须覆盖 template 的错误检出与 SFC 构建；矩阵先按 4.2 重新批准。

三个默认组合为 vanilla/npm/7、react/npm/7、vue/npm/7。完整 `check:milestone` 只对这三个不同组合执行，放在 Ubuntu 的 milestone job；B–G 不运行昂贵的全套变异，但按 9 节保留补坑检查的针对性验收。默认 milestone 内部已含 full，不重复声称 mutation-only 是完整 milestone。

| ------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------- |
| `ci.yml / checks`                     | 根 vanilla/npm/7，Ubuntu、macOS、Windows | 保留现有根 `check:full`，实际构建与 Chromium                                              | 5–15 分钟 / 25 分钟                |

这保留了当前三个默认成品的三系统保障，选项兼容性以 6 组 pairwise 加 G 取得。macOS/Windows 额外测试 G，未声称所有 12 组都经过三系统安装。根 full 与生成 vanilla full 各自验证不同入口，先保留重复成本；若要复用，必须以相同输入及目标证明等效，另行批准，不能本轮自行删根门。

现有 `ci.yml / milestone` 的 mutation-only 调度迁入生成默认组合的完整 milestone，避免 CI 仍偷偷对其它组合跑完整里程碑。保留所有原模型、可访问性和 Vue 负例，拆分调度不等于删除测试。框架、lint 或管理器适配改动影响某个抽样外组合时，临时追加该组合 full；pairwise 不替代准确待合入版本的适用全量。

npm job 用 setup-node 及固定 npm；Bun job 同样先准备 Node，再使用已校验校验和的固定 Bun 1.3.11 二进制，拟用下载流程不新增未定版本的 action。若选择 setup-bun，必须先列精确 action commit 和许可证另行批准。维护器仍 `npm ci --prefix tools/template-tests`。缓存按 OS、架构、管理器精确版本、锁哈希分离，不能共享 node_modules。Bun 的 `--frozen-lockfile` 语义依据 [Bun install](https://bun.sh/docs/pm/cli/install)，具体 1.3.11 仍须实测。

每 job 使用独立源码 fixture、giget 目的地、依赖树、`dist/` 和端口。Playwright 只操作该次生产构建的服务器，核对身份，等待公开完成信号。证据按组合、OS、尝试编号写入 `artifacts/template-contracts/`，锁生成写 `artifacts/template-locks/`，模型变异报告进 `reports/`。无论成功失败均上传命令、cwd、版本、exit、signal、stdout/stderr 和锁前后哈希，不让并发 job 覆盖同名证据。

12 组的廉价检查不需要给每组安装依赖，也不需要下载两版编译器；使用维护器和已记录的静态配置策略。它只能证明静态契约，不能当作这 12 组都通过 tsc、真实安装或浏览器验收。

`no-explicit-any`、`no-non-null-assertion`、`consistent-type-imports`、`ban-ts-comment`、React Hooks、JSX 可访问性、复杂度和深度规则仍归 Oxlint 的非类型阶段，不挪到 ESLint。两种 lint 阶段都保留 warnings 非零、未使用 disable 指令检出；不得为分拆 lint 放宽原注释说明长度。

| 维度                | a：TS 6 继续用 TS 7 的 oxlint-tsgolint                                        | b：非类型 Oxlint，加与编译器匹配的类型阶段，推荐                                                                                                             |
| ------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| 速度                | 预期工程启动与类型阶段成本较低，未测量                                        | TS 6 的 project service 加 Node lint 预计较慢；TS 7 分阶段有重复扫描；真实差值待实验                                                                         |

### 7.3 实验设计，本阶段不安装、不执行

批准安装后，在互不共享依赖的 `a-ts6`、`b-ts6`、`ts7-control` 目录准备相同虚构源码，每个只有自己的锁。原应用 fixture、实验输入、输出、服务器与证据分离。固定 Node 26.13.1、两版 TS、两种 lint 的精确版本、相同 CPU 限额和同一源码哈希。实验只比较真实 lint 工作，不把安装或下载计入 lint 用时。

先跑正确性，再测速度。最小样例集如下。

| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 普通安全与违规对       | 22 条各一对，含 await/catch、void 配置、thenable、穷尽 union、JSON unknown 解析及 DOM 边界；违规须先 `tsc` 成功再使 lint 非零                 | 所有既有负例和新增逐规则样例必须检出；不能把编译/配置失败计为 lint 抓错                                                                                 |

Unicode 插值样例设计如下，只作为未来实验 fixture，本阶段未执行。正例对照把 `part` 明确声明为 string，两版均不得报这两条规则。

```ts
type Head<S extends string> = S extends `${infer H}${infer _T}` ? H : never;
type Rendered = Head<'😀abc'> extends '😀' ? { value: number } : string;
declare const part: Rendered;

```

Unicode 差异来自 [TS 7 Unicode 说明](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#template-literal-types-now-preserve-unicode-code-points)；排序样例及诊断 flag 来自 [TS 6 排序说明](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/#the-stabletypeordering-flag)。插值样例的具体诊断为实验预期，未执行验证，不把文档中的语言差异直接当作已证实的 linter 误报。

每个隔离目录先运行 `node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json --pretty false`；a 运行本地 `oxlint --type-aware --format=json <受控文件列表>`；b 的公共配置不启用类型规则，依次运行本地 `oxlint --format=json <相同列表>`、`node node_modules/eslint/bin/eslint.js --max-warnings 0 --format json <相同列表>`。真实 lint 门保留 deny-warnings 和 unused-disable 检查。这里只展示命令形状，`<受控文件列表>` 在实验任务单中替换成仓库现有清单，不执行未固定版本的 npx。

declaration 测试在实验配置中将 `noEmit` 改为 false，开启 declaration 和 emitDeclarationOnly，输出各自独立目录；stable 变化仅在实验配置中发生，不给生产维护两套 tsconfig。每次保存有效配置、输入哈希、工具版本、退出码、原 stdout/stderr、JSON 诊断、declaration 输出和时间。汇总为「版本 × 规则 × 文件位置 × 正误样例 × 期望 × 实际 × 分歧原因」，不要只报告错误条数。

正确性通过后，每种 lint 冷启动 5 次、预热后 10 次，交替 a/b 顺序，禁止 lint cache，记录中位数、逐次最大值、峰值内存和每次文件数。10 次样本的 P95 仅作粗略信号，不宣称稳定尾延迟。另跑未放大模板与按明确倍数生成的独立大样本，不能用小模板的进程启动成本推断大工程速度。预先建议预算为本模板 b 的快检相对 a 中位数增加不超过 3 秒，放大样本 P95 不超过 a 的 2 倍，交 Nika 批准后采用。预算不是实测结论，也不授权降低规则强度。

选择门槛：现有保护与 22 条负例全部检出、合法样例无未解释误报、文件集合一致、b 的类型服务确实使用 TS 6。Unicode 等已知版本差异单独登记，不强求两版本诊断文本完全一致。任何未知漏报、无法解释的配置失败或超预算都停止定案并交回；a 只有在风险明确可接受并获 Nika 批准后才可代替 b。

## 9. Stryker 防回退快检

建议在 `scaffold/common/tools/checks/toolchain.ts` 集中实现共享工具策略，将 `check:toolchain` 接入 `scaffold/common/package.json` 的 `check`，放在 format 后、lint/typecheck 前，及早输出故障原因。规则读取项目实际 `stryker.config.json`，必须为 JSON 对象、拥有自己的 `tsconfigFile` 字段，值严格等于空字符串。字段缺失、null、false、空格、任意路径、配置缺失或无效 JSON 均非零；不隐式使用 Stryker 默认值。若未来引入 JS 配置，不默认执行任意配置代码，须重新设计解析边界。

> Stryker 10.1.1 的 tsconfig 预处理调用 TS 6 编译器 API，TS 7 已删除这些接口。stryker.config.json 必须显式设置 "tsconfigFile": ""，再运行所选管理器的 run check。不要只删字段。上游修复：https://github.com/stryker-mutator/stryker-js/pull/6231 。

1. 原故障回放：获准的 TS 7 独立 fixture 去掉空字符串，直接运行真实 mutation，保存旧 API 错误；恢复字段后同一工具版本 mutation 成功且模型分数仍 100%。已有任务单报告的 13:33 成功只算他人提供线索，本次没有复跑。
